# 調査結果: タスク削除

## 既存構成の確認

- フロントエンドはReact 19 + TypeScript + Viteで、タスク一覧と登録フォームは`App.tsx`にある。`taskApi.ts`には一覧取得と登録だけがあり、削除API呼び出しはない。
- バックエンドの`TaskSkeletonController`は一覧で空配列を返すスケルトンである。タスクの永続化層、依存関係の永続化層、Flywayマイグレーションはまだ存在しない。
- `docs/design/api-contract.md`は削除を`DELETE /api/tasks/{taskId}`、成功を204、対象不在・論理削除済みを404と定義する。
- `docs/design/data-model.md`およびADR-003は論理削除、通常一覧からの除外、実績記録の保持、削除対象に接続する依存関係の除去を定義する。S3-11に従い、削除対象を経由する関係をつなぎ直さない。
- `.github/dependabot.yml`はnpm依存関係を日次で確認する。削除フローに新たなnpm依存は必要ないため、設定変更は行わない。

## 設計上の決定

### 1. 論理削除と関連データの整合性

- **決定**: タスクに削除日時を記録して通常一覧から除外する。対象タスクを先行または後続とする依存関係を削除し、実績記録と無関係な依存関係は保持する。削除対象を経由する関係を自動でつなぎ直さない。
- **理由**: 採用済みのADR-003と共通データモデルがこのライフサイクルを定義している。履歴を保持し、削除対象以外への影響を限定できる。
- **検討した代替案**: 物理削除は保持すべき実績記録と参照整合性に反する。関連関係の自動再接続は既存契約で明示的に行わない。

### 2. 削除確認後にのみAPIを呼び出す

- **決定**: 一覧の削除操作で対象タスク名を示す確認を表示する。確定時のみDELETEを呼び、キャンセル時には呼び出さない。確認はブラウザー標準の`window.confirm`で実現する。
- **理由**: 確認とキャンセルの動作は仕様上必須である。既存画面に確認ダイアログ部品やUIライブラリがなく、標準機能なら依存追加や重複コンポーネントを避けられる。
- **検討した代替案**: 独自のモーダルは一貫したデザインが必要な場合に適するが、この要件では新たな状態管理・スタイル・テスト負担を増やすため採用しない。

### 3. 既存のREST契約を使う

- **決定**: `DELETE /api/tasks/{taskId}`を使用し、成功時は204（本文なし）、対象不在または削除済みは404を返す。画面は成功後に一覧から対象を除くか再取得する。
- **理由**: パス、結果、エラー方針は既存API契約とADR-003に定義済み。削除成功のメッセージはクライアント側で表示する。
- **検討した代替案**: 削除対象をリクエスト本文で送る、または成功時にタスク本文を返す方式は既存契約を変更するため採用しない。

### 4. 登録機能・共通永続化機能との境界

- **決定**: この機能は削除操作に限定し、登録画面/APIやサンプルタスク登録を追加しない。既存タスクと依存関係を提供する共通永続化基盤との統合を実装前提として確認する。
- **理由**: 現在のコードは永続化を持たず、一覧も空である一方、削除には既存レコードが必要である。登録を混ぜず、実データとテスト用fixtureの供給元を明確にする。
- **検討した代替案**: 削除フロー内で暗黙にタスクを作る案は対象外要件に反する。存在しない対象に対して成功を返す案は404契約に反する。

## 未解決事項

- タスクと依存関係の永続化層、および削除対象を一覧で提供する基盤がどの先行機能から提供されるか、実装着手前にチームで確認する。削除機能に登録処理を含めることを意味しない。
- 既存の設計資料以外に必要な技術選定や外部サービス連携はない。
