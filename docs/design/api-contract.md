# API契約

- 対象: Must M1-M3、Should S1-S3
- 方針: [ADR-003](../adr/ADR-003-data-model-and-api.md)および[データモデル](./data-model.md)に基づく。
- 実装順: Mustを先に実装し、その後Should S1〜S3を実装する。Shouldのデータ/API設計は採用済みで、個別の実装順・担当者・見積りはWBSで決定する。
- ベースパス: `/api`
- データ形式: JSON

## 共通ルール

- 日付は`YYYY-MM-DD`形式とする。未来日を許可しない実績日など、受け入れ条件に応じた検証を行う。
- タスク名は必須で、前後のUnicode空白を除去して保存する。未入力、除去後に空となる値、および除去後100文字（Unicodeコードポイント数）を超える値を拒否する。
- 説明は省略または`null`を許可し、入力値が200文字（Unicodeコードポイント数）を超える場合は拒否する。
- 入力検証はバックエンドでも行う。画面側の検証だけで有効性を保証しない。
- 論理削除済みタスクは通常の一覧に含めず、個別取得や更新の対象にも含めない。
- 登録・更新は一つの処理として行う。失敗時に一部だけ保存せず、成功したような応答を返さない。
- 成功・失敗のメッセージや確認ダイアログは画面側で表示する。削除キャンセル時は削除APIを呼び出さない。

## 共通エラー応答

```json
{
  "code": "VALIDATION_ERROR",
  "message": "入力内容を確認してください。",
  "fieldErrors": {
    "taskName": "タスク名は必須です。"
  }
}
```

`fieldErrors`は項目別のエラーがある場合に返す。

| HTTPステータス | 用途 |
|---|---|
| 400 Bad Request | 必須項目不足、形式不正、文字数・数値条件違反 |
| 404 Not Found | タスク、実績記録、依存関係が存在しない、または論理削除済み |
| 409 Conflict | 重複・循環依存など、現在の状態と競合する操作 |
| 500 Internal Server Error | 予期しない処理失敗。成功扱いにせず、部分更新を残さない |

## Task表現

### Must

```json
{
  "taskId": 101,
  "taskName": "API契約を確認する",
  "description": null,
  "dueDate": "2026-11-18"
}
```

### Should機能を実装した場合の追加項目

以下はShould機能を実装する場合の表現例であり、実装対象外の機能に対応する項目は含めない。

```json
{
  "status": "NOT_STARTED",
  "assigneeName": null,
  "estimatedMinutes": 60,
  "actualTotalMinutes": 0,
  "parallelStatus": "READY",
  "parallelStatusWarning": null
}
```

- `status`: `NOT_STARTED`、`IN_PROGRESS`、`COMPLETED`のいずれか。画面ではそれぞれ「未着手」「実行中」「完了」と表示する。
- `assigneeName`: 自由入力。未設定は`null`で、画面では「未割当」と表示する。
- `estimatedMinutes`、`actualTotalMinutes`: 0以上の整数分数。製品上の上限は設けない。
- `parallelStatus`: `READY`、`BLOCKED`、`IN_PROGRESS`、`COMPLETED`、`UNKNOWN`のいずれか。画面ではそれぞれ「並列作業可能」「並列作業不可」「実行中」「完了」「判定不能」と表示する。
- `parallelStatusWarning`: 判定不能の理由を画面に示す場合に返す任意項目。

## Must: タスク管理（「タスクの登録」M1-01〜M1-08／「タスクの更新」M2-01〜M2-09／「タスクの削除」M3-01〜M3-06）

| 操作 | メソッド・パス | 成功応答 | 主な受け入れ条件 |
|---|---|---|---|
| タスク一覧 | `GET /api/tasks` | 200、`{"items": [Task, ...]}` | M1-04、M2-04、M3-04 |
| タスク登録 | `POST /api/tasks` | 201、作成したTask。`Location: /api/tasks/{taskId}`を返す | M1-01〜M1-08 |
| タスク取得 | `GET /api/tasks/{taskId}` | 200、Task | M2-01 |
| タスク更新 | `PUT /api/tasks/{taskId}` | 200、更新後のTask | M2-02〜M2-09 |
| タスク削除 | `DELETE /api/tasks/{taskId}` | 204、本文なし。論理削除する | M3-01〜M3-06 |

登録・更新リクエスト:

```json
{
  "taskName": "API契約を確認する",
  "description": "入出力とエラー応答を確認する",
  "dueDate": "2026-11-18"
}
```

- `taskName`と`dueDate`は必須。`description`は省略または`null`を許可する。
- M1-05／M2-05: `taskName`が未入力、空白文字のみ、または`dueDate`が未入力の場合、400を返し保存しない。
- M1-06／M2-06: 前後のUnicode空白を除去した`taskName`が100文字（Unicodeコードポイント数）を超える場合、400を返し保存しない。
- M1-07／M2-07: `description`が200文字（Unicodeコードポイント数）を超える場合、400を返し保存しない。
- M1-08／M2-08: `dueDate`が実在しない日付または`YYYY-MM-DD`以外の形式の場合、400を返し保存しない。
- `PUT`は編集可能なMust項目を全て受け取る。任意の説明が省略または`null`の場合は空として扱う。
- M2-09: 更新対象のタスクが存在しない場合、404を返し他のタスクを変更しない。
- M3-06: 削除対象のタスクが存在しない場合、404を返し他のタスクを変更しない。
- 削除時は論理削除日時を設定し、関連する依存関係を削除する。実績記録は保持する。
- 削除確認は画面側で行う。キャンセル時はAPIを呼び出さない。

## Should S1: 各タスクの作業時間の可視化（S1-01〜S1-12）

### 見積り（S1-01「見積り登録」・S1-02「見積り編集」）

| 操作 | メソッド・パス | 成功応答 | 受け入れ条件 |
|---|---|---|---|
| 見積り登録・編集 | `PUT /api/tasks/{taskId}/estimate` | 200、`{"estimatedMinutes": 60}` | S1-01「見積り登録」、S1-02「見積り編集」 |

リクエスト:

```json
{
  "estimatedMinutes": 60
}
```

値は0以上の整数分数とし、製品上の最大値は設けない。見積りの更新は実績記録や他タスクを変更しない。

### 実績記録（S1-03〜S1-12）

| 操作 | メソッド・パス | 成功応答 | 受け入れ条件 |
|---|---|---|---|
| 実績と合計の取得 | `GET /api/tasks/{taskId}/work-logs` | 200、実績記録一覧と`actualTotalMinutes` | S1-04「実績時間の累積」、S1-06「時間情報の識別表示」、S1-07「保存後の維持」 |
| 実績登録 | `POST /api/tasks/{taskId}/work-logs` | 201、作成した記録と更新後の合計 | S1-03「日付付き実績の記録」、S1-04「実績時間の累積」、S1-08「時間入力の境界値」、S1-09「不正な時間値」、S1-10「日付の入力検証」、S1-11「失敗時の整合性」、S1-12「対象タスクが存在しない場合」 |
| 実績編集 | `PUT /api/tasks/{taskId}/work-logs/{workLogId}` | 200、更新した記録と更新後の合計 | S1-05「実績記録の編集」、S1-06「時間情報の識別表示」、S1-07「保存後の維持」、S1-08「時間入力の境界値」、S1-09「不正な時間値」、S1-10「日付の入力検証」、S1-11「失敗時の整合性」、S1-12「対象タスクが存在しない場合」 |

取得レスポンス例:

```json
{
  "items": [
    {
      "workLogId": 401,
      "workDate": "2026-11-17",
      "minutes": 45
    }
  ],
  "actualTotalMinutes": 45
}
```

登録・編集リクエスト:

```json
{
  "workDate": "2026-11-17",
  "minutes": 45
}
```

- 実績日は必須で、実在しない日付・未来日は400として拒否する。
- `minutes`は0以上の整数分数とし、数値でない値、負数、小数は400として拒否する。製品上の最大値は設けない。
- 更新後の`actualTotalMinutes`は、全実績記録を再集計して返す。
- タスクまたは実績記録が存在しない場合は404とし、他のデータを変更しない。

## Should S2: AI開発の並列作業の可視化（S2-01〜S2-17）

| 操作 | メソッド・パス | 成功応答 | 受け入れ条件 |
|---|---|---|---|
| 一覧・再判定・絞り込み | `GET /api/tasks`（`parallelStatus`は任意） | 200、`{"items": [Task, ...]}` | S2-01〜S2-17 |

`GET /api/tasks`に任意のクエリを追加する。

```text
GET /api/tasks?parallelStatus=READY
```

- タスク一覧には`taskName`、`status`、`assigneeName`、`dueDate`、`parallelStatus`を含める。
- `parallelStatus`は`READY`、`BLOCKED`、`IN_PROGRESS`、`COMPLETED`、`UNKNOWN`で絞り込む。
- `READY`は未着手で先行タスクがない、または全て完了済みのタスク。`BLOCKED`は未完了の先行タスクがあるタスク。
- 完了済み・実行中タスクはそれぞれ`COMPLETED`・`IN_PROGRESS`とし、READY／BLOCKEDには分類しない。
- 必要な依存関係情報が個別タスクについて不正・不明な場合は`UNKNOWN`とし、問題の警告情報を返す。
- 判定不能の場合は、必要に応じて`parallelStatusWarning`に理由を設定し、画面で利用者に示す。
- 一覧取得や再判定そのものに失敗した場合はエラー応答を返し、前回の判定結果を最新として返さない。
- 絞り込み結果が空の場合は200と空の`items`を返す。`parallelStatus=READY`で結果がない場合、画面は「現在、並列に着手可能なタスクはありません」と表示する。
- 論理削除済みタスクは一覧・再判定に含めない。担当者が未入力のタスクは除外せず、画面で「未割当」と表示する。

### ステータス・担当者の更新（S2-06、S2-07、S2-08、S2-09、S2-13）

| 操作 | メソッド・パス | 成功応答 |
|---|---|---|
| ステータス・担当者の更新 | `PATCH /api/tasks/{taskId}` | 200、更新後のTask |

```json
{
  "status": "IN_PROGRESS",
  "assigneeName": "参加者A"
}
```

- `status`と`assigneeName`の一方だけを指定して更新できる。
- `status`は定義済みの3値のみ受け付ける。`assigneeName`は自由入力で、未割当への変更は`null`または空文字で指定する。

## Should S3: タスクの依存関係の可視化（S3-1〜S3-10）

| 操作 | メソッド・パス | 成功応答 | 受け入れ条件 |
|---|---|---|---|
| 依存関係一覧 | `GET /api/tasks/{taskId}/dependencies` | 200、先行・後続タスク一覧 | S3-3「関係の一覧表示」、S3-4「登録結果の維持」、S3-5「依存関係がないタスク」 |
| 依存関係登録 | `POST /api/task-dependencies` | 201、作成した関係 | S3-1「依存関係の登録」、S3-2「複数の依存関係」、S3-6「自己依存・循環依存の拒否」、S3-7「重複する依存関係」、S3-8「存在しないタスク」、S3-9「失敗時の整合性」 |
| 依存関係編集 | `PUT /api/task-dependencies/{predecessorTaskId}/{successorTaskId}` | 200、更新後の関係 | S3-4「登録結果の維持」、S3-6「自己依存・循環依存の拒否」、S3-8「存在しないタスク」、S3-9「失敗時の整合性」、S3-10「依存関係の編集・解除」 |
| 依存関係解除 | `DELETE /api/task-dependencies/{predecessorTaskId}/{successorTaskId}` | 204、本文なし | S3-9「失敗時の整合性」、S3-10「依存関係の編集・解除」 |

依存関係一覧のレスポンス例:

```json
{
  "predecessors": [
    {
      "taskId": 101,
      "taskName": "先行タスク"
    }
  ],
  "successors": []
}
```

依存関係がない場合は、`predecessors`と`successors`の両方を空配列で返す。

登録リクエスト:

```json
{
  "predecessorTaskId": 101,
  "successorTaskId": 102
}
```

- 1つのタスクに登録できる依存関係の数に上限を設けない。
- 編集時のパスは編集対象の現在の関係を示し、リクエスト本文には変更後の関係を指定する。

編集リクエスト例:

```json
{
  "predecessorTaskId": 103,
  "successorTaskId": 102
}
```

- 先行・後続の両タスクが存在し、論理削除されていないことを確認する。
- 自己依存、循環依存、存在しないタスクへの関係は拒否する。
- 同一関係が既に存在する場合は409とし、既存関係を変更しない。
- 関係がない場合は空の先行・後続一覧を返し、画面では依存関係がないことを明示する。
- 編集・解除は対象の関係だけを変更または削除し、関係先のタスク自体は削除しない。
- 登録・編集・解除に失敗した場合は部分更新を行わない。

## 画面側の責務

- タスク登録画面にはタスク名・説明・期限日の入力欄を表示し、編集時には対象タスクの現在の情報を表示する。
- 登録・更新・削除の完了メッセージ、削除確認、入力欄ごとのエラー表示を行う。
- 登録・更新・削除が成功した場合、それぞれの完了メッセージを表示する。削除確認でキャンセルした場合はタスクを削除しない。
- 見積りと実績合計を区別して表示し、各実績の作業日と分数を確認できるようにする。時間情報の保存・編集後や画面再表示時には保存済みの値を表示する。
- `GET /api/tasks`の成功時にのみ一覧を最新化する。取得・再判定に失敗した場合は、成功したように表示しない。
- 一覧取得または並列作業状態の再判定に失敗した場合、最新情報を取得できていない旨を表示し、前回の判定結果を最新として表示しない。
- `parallelStatus=READY`の絞り込み結果がない場合は、受け入れ条件どおり「現在、並列に着手可能なタスクはありません」と表示する。
- 依存関係がない場合はその状態を明示し、別タスクの関係を表示しない。依存関係の登録・編集・解除に失敗した場合はエラーを表示する。

| API契約の項目 | 受け入れ条件の項目 |
|---|---|
| Must: タスク登録 | 「タスクの登録」M1-01〜M1-08 |
| Must: タスク取得・更新 | 「タスクの更新」M2-01〜M2-09 |
| Must: タスク一覧 | 「タスクの登録」M1-04、「タスクの更新」M2-04、「タスクの削除」M3-04 |
| Must: タスク削除 | 「タスクの削除」M3-01〜M3-06 |
| Should S1: 見積り・実績記録 | 「各タスクの作業時間の可視化」S1-01〜S1-12 |
| Should S2: 状態表示・絞り込み・再判定 | 「AI開発の並列作業の可視化」S2-01〜S2-17 |
| Should S3: 依存関係の参照・登録・編集・解除 | 「タスクの依存関係の可視化」S3-1〜S3-10 |
