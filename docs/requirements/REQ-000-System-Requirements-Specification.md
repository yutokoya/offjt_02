## 1. 目的

本書は、研修受講者向けタスク管理システムの目的、機能要件、非機能要件、データ、システム構成およびテスト方針を定義する。機能別の受け入れ条件と詳細は、本書と併せて参照する個別要件定義書に記載する。

### 1.1 ドキュメントの適用範囲

本書の対象範囲は、タスクの登録・更新・削除、作業時間の記録、タスク依存関係の管理、および依存関係に基づく並列作業状態の表示である。本書に記載のない機能は初期リリースの対象外とし、追加する場合は本書を改訂する。

AI利用費用の集計・可視化はAs-Is上の課題として認識するが、初期リリースの対象外とする。対象に含める場合は、機能要件、受け入れ条件および関連するデータ・API仕様を追加する。

機能別の詳細要件：

- Must（必須）：[タスク登録（REQ-UC001）](./REQ-UC001-タスク登録.md)、[タスク更新（REQ-UC002）](./REQ-UC002-タスク更新.md)、[タスク削除（REQ-UC003）](./REQ-UC003-タスク削除.md)
- Should（推奨）：[作業時間の可視化（REQ-UC004）](./REQ-UC004-作業時間の可視化.md)、[並列作業の可視化（REQ-UC005）](./REQ-UC005-並列作業の可視化.md)、[タスク依存関係の可視化（REQ-UC006）](./REQ-UC006-タスク依存関係の可視化.md)

### 1.2 想定読者

- 研修受講者および業務関係者
- 開発チーム
- プロジェクト管理者
- 品質保証・テスト担当者

## 2. システム概要

### 2.1 システムの目的

研修で扱うタスク、期限、作業時間、タスク間の依存関係を一元的に管理する。受講者が進捗と作業順序を把握し、複数人で作業を計画・分担できるようにする。

**As-Is（現状）**

現在、研修参加者4名はAI開発プロジェクトにおいてタスク管理を個別に実施しており、タスクの依存関係や担当者の状況をリアルタイムに把握できていない。

そのため、

- どのタスクから着手可能か判断するためにメンバー間で確認が必要となる
- 先行タスクの完了待ちによる待機時間が発生する
- 並列で実施可能な作業を見落とし、生産性が低下する
- 作業時間の見積りと実績が管理されておらず、工数超過や遅延の原因分析ができない
- AI利用費用やタスクごとの工数を個別管理しているため、プロジェクト全体の状況を把握しにくい

結果として、研修参加者は開発作業よりも進捗確認や調整に時間を費やしており、タスク着手までの平均待ち時間が約3時間発生している。

### 2.2 主要機能

以下は本システムで実現する要件上の機能であり、現行コードの実装済み機能を示すものではない。

1. タスクの登録、一覧表示、更新、削除
2. タスクごとの見積り時間および日付付き実績時間の記録・表示
3. 依存関係とタスク状態に基づく並列作業状態の判定、表示、絞り込み
4. タスク間の先行・後続関係の登録・表示・編集・解除
5. 入力検証、処理結果およびエラーの利用者への通知

### 2.3 対象ユーザー

- **研修受講者（4名）**：タスクを登録・更新・削除し、時間情報や依存関係を管理して、タスクの進捗および並列作業状態を確認する唯一の業務利用者。4名は同時利用者数の上限とする。
- **運用管理者**：インフラ、バックアップ、監視を担当する。タスク管理画面の利用者ではなく、アプリケーション内の管理機能は初期リリースの対象外とする。

## 4. 機能要件

### 4.1 業務フロー

#### 4.1.1 基本的なフロー

1. 研修受講者がタスクを登録・一覧確認し、必要に応じて更新または確認後に削除する。
2. Should機能では見積り・実績時間および依存関係を記録・編集・解除する。
3. システムが最新のタスク状態と依存関係から並列作業状態を判定・表示する。

### 4.2 ユースケース

機能別の受け入れ条件と詳細フローは、各要件定義書を参照する。

| ユースケース | 要件定義書 | 概要 |
|---|---|---|
| UC001：タスク登録 | [REQ-UC001](./REQ-UC001-タスク登録.md) | タスク名、説明、担当者、期限日を入力して登録し、一覧で確認する。 |
| UC002：タスク更新 | [REQ-UC002](./REQ-UC002-タスク更新.md) | 登録済みタスクの情報を確認・更新する。 |
| UC003：タスク削除 | [REQ-UC003](./REQ-UC003-タスク削除.md) | 確認後に対象タスクを論理削除する。 |
| UC004：作業時間の可視化 | [REQ-UC004](./REQ-UC004-作業時間の可視化.md) | 見積り時間と日付付き実績時間を管理し、実績合計と差異を確認する。 |
| UC005：並列作業の可視化 | [REQ-UC005](./REQ-UC005-並列作業の可視化.md) | 依存関係に基づく並列作業状態を表示・絞り込みする。 |
| UC006：依存関係の可視化 | [REQ-UC006](./REQ-UC006-タスク依存関係の可視化.md) | タスク間の先行・後続関係を登録・確認・編集・解除する。 |

### 4.3 業務ルール

#### 4.3.1 タスク情報

- タスク名と期限日は登録時の必須項目である。説明は入力欄を提供するが、必須とは定めない。
- 担当者はMust要件として登録・更新できる任意の自由入力項目とし、未設定も許可する。
- タスク名は前後のUnicode空白文字を除去して保存し、除去後に空となる値は受け付けない。タスク名は除去後100 Unicodeコードポイント以内、説明は入力値そのものを200 Unicodeコードポイント以内とする。
- 期限日は有効な日付でなければならない。過去日も登録・更新できる。
- タスク状態は「未着手」「実行中」「完了」の3種類とし、新規登録時は「未着手」とする。研修受講者は3状態間を任意に変更できる。
- タスク削除は論理削除とし、削除確認でキャンセルされた場合は変更しない。論理削除済みタスクは通常の一覧に表示しない。

#### 4.3.2 作業時間

- 実績は日付必須、0以上の整数分で記録し、実在しない日付・未来日を拒否する。製品上の最大値は設けず、実績合計は全記録の合計と一致させる。
- 見積り時間は実績と別に管理する任意項目とし、登録時は0以上の整数分、上限なしとする。

#### 4.3.3 依存関係・並列作業状態

- 依存関係は「先行タスク → 後続タスク」とし、複数登録を許可する。同一関係の重複、自己依存、循環依存、存在しないタスクへの参照は登録しない。
- 並列作業状態は最新のタスク状態・依存関係から判定する。不正な依存関係があれば「判定不能」とし、「可能」「不可」と誤表示しない。
- 「判定不能」「実行中」「完了」は「並列作業可能」「並列作業不可」と区別して表示する。

### 4.4 エンティティ

#### 4.4.1 タスク

**主要データ項目：**

| 項目 | 説明 | 制約・補足 |
|---|---|---|
| タスク識別子 | タスクを一意に識別する値 | PostgreSQLの`BIGINT` identityで採番し、APIでは数値の`taskId`として扱う。削除後も再利用せず、ロールバック等による欠番は許容する。 |
| タスク名 | タスクの名称 | 必須。最大100文字 |
| 説明 | タスクの説明 | 任意。最大200文字 |
| 期限日 | タスクの期限 | 登録時必須。有効な日付 |
| ステータス | タスクの進行状態 | 未着手、実行中、完了|
| 担当者 | タスク担当者 | M1/M2のMust要件で任意入力・登録・更新し、S2の一覧では未設定を「未割当」と表示 |

#### 4.4.2 作業時間情報

- **時間情報：** 見積りは任意の0以上の整数分（上限なし）。実績は日付と0以上の整数分の組で複数記録を許容し、実績合計は全記録から算出する。

#### 4.4.3 タスク依存関係

- **依存関係：** 先行・後続タスク識別子による有向関係をPostgreSQLの依存関係テーブルに保持し、両IDに外部キーを設定する。
- 1タスク当たり複数関係を許可し上限は設けない。同一組み合わせは一意制約で、自己依存はDB制約で、循環依存はアプリケーションで拒否する。

### 4.5 その他要件

#### 4.5.1 ユーザーインターフェース

- タスク登録画面にタスク名、説明、担当者、期限日の入力欄を設ける。エラー・処理失敗・登録／更新／削除の完了を表示し、削除前に確認とキャンセルを提供する。
- 見積り・実績を区別し、実績の日付・分数を表示する。両方登録時は同じ画面で大小と差異を示し、更新後に再計算する。一方が未登録なら「未算出」とする。
- 並列作業状態の「可能」「不可」「実行中」「完了」「判定不能」を識別できるよう表示する。
- 初期リリースではデスクトップ版のChromeおよびEdgeの最新2メジャーバージョンをサポートし、画面幅1024px以上で主要操作を完了できること。主要操作はキーボードでも実行できること。

#### 4.5.2 データ管理

- 登録・更新情報は再表示時も保持し、検証・処理失敗時に部分更新しない。依存関係の編集・解除で関係先タスクを削除しない。
- 削除時はタスクに論理削除日時を設定し、接続する依存関係だけを削除する。無関係な関係、実績記録、他タスクは保持する。
- DBはPostgreSQL、スキーマ変更はFlywayで管理し、Hibernateの自動更新を併用しない。論理削除済みタスクは通常画面・業務APIから取得・更新できず、タスクと実績はDB・バックアップに保持する（バックアップ世代の期限超過後は除去）。

## 5. 非機能要件

以下は初期リリースの受け入れ目標とする。実運用で目標を超える利用が必要になった場合は、容量・性能要件を見直す。

### 5.1 業務処理量条件

- **利用者・性能試験データ量：** 研修受講者4名の同時利用、有効タスク1,000件、実績記録10,000件、依存関係5,000件を基準とする。
- **保持期間：** タスク本体と実績は論理削除後もDBに保持し、自動物理削除しない。
- 上記データ量は性能試験の基準であり、アプリケーション上の登録件数上限とはしない。

### 5.2 性能条件

- 5.1の利用条件で、一覧・詳細・登録・更新・削除APIの応答時間は95パーセンタイル2秒以内、計画メンテナンスを除く月間稼働率は99.0%以上とする（稼働時間は毎日8:00～20:00 JST）。
- 並列作業状態は一覧の初回表示・再読み込み・再表示時に最新のタスク情報と依存関係から判定する。

### 5.3 信頼性条件

- 入力検証・処理失敗・対象不存在時は成功扱いや部分更新をせず、利用者にエラーを通知する。
- DBを毎日バックアップし、直近7日分を本番ホスト外に保持する。RPOは24時間以内、RTOは障害検知から1営業日以内とし、復元を四半期ごとに確認する。

### 5.4 セキュリティ条件

- アプリ内のアカウント・ロール管理は提供せず、ホスティング環境で研修受講者4名にアクセスを限定する。インターネットへ直接公開せず、閉域網またはVPN経由でHTTPSを使用する。
- タスク名、担当者名、説明に認証情報や要配慮個人情報などの機密情報を入力しない。

### 5.5 外部連携条件

- 外部API・他システム・通知サービスとは連携せず、フロントエンドとバックエンド間はREST APIを使用する。
- 現行バックエンドはヘルスチェック用`GET /health`のみ実装済みで、タスク管理APIは未実装。詳細API・DB接続方式は実装設計時に定義する。

### 5.6 移行条件

- 既存システムからのデータ移行は行わない。初期データのない状態で稼働を開始し、研修受講者が必要なタスクを登録する。

### 5.7 保守運用条件

- 運用管理者はヘルスチェックを監視し、障害復旧・バックアップ復元を行う。バックアップ成否を毎日確認し、復元手順を文書化する。
- アプリケーションログには機密情報を記録せず、30日間保持する。

### 5.8 拡張性条件

- 初期リリースは4名同時利用・5.1の試験データ量を対象とし、自動スケールや複数ノード構成は要求しない。基準を超える場合は増強前に性能・容量要件を改訂する。
- 新しいステータス、タスク属性、機能を追加する場合は本書と関連要件を更新する。

## 6. テスト方針

### 6.1 テスト自動化方針

正常系、入力エラー、対象不存在、処理失敗、データ整合性を受け入れ条件ごとに検証する。フロントエンドはVitest／React Testing Library（`pnpm test`）、バックエンドはJUnit 5／Spring Boot Test（`./mvnw verify`）を使用し、CIで両者のビルド・テストとlintを実行する。

現行CIはフロントエンドのlint・ビルド、バックエンドの`verify`を実行するが、フロントエンドのテストスクリプトとバックエンドlintは未設定。バックエンドには起動・ヘルスチェックのテストがあるが、タスク管理機能のテストは未実装。

### 6.2 単体テスト

入力検証、時間合計、依存関係、並列状態を対象とし、必須値・文字数・日付、担当者の設定／変更／解除、0以上の整数分、自己・循環・重複・不存在の依存関係、および依存関係と状態別の判定を検証する。

### 6.3 データ連携テスト

PostgreSQLで登録・取得・更新・削除、失敗時の部分更新防止、Flywayマイグレーション、および複数同時登録時のID重複防止・削除済みID非再利用を検証する。

### 6.4 統合シナリオテスト

利用者の画面操作からREST API、PostgreSQLへの保存・再表示までの主要フローを検証する。

- タスク登録・更新後に最新情報を一覧で確認する。削除確定時は一覧・取得対象から除外され、実績は保持、接続する依存関係だけが削除されること、キャンセル時は変更されないことを確認する。
- 時間情報の登録・編集後に再表示し、実績合計が各記録の合計と一致することを確認する。
- 依存関係変更および先行タスク完了後、最新情報に基づき並列状態が再判定され、先行タスクがすべて完了した後続タスクが「並列作業可能」と表示されることを確認する。

### 6.5 リリース条件

- Must（M1〜M3）およびリリース対象とするShould要件の受け入れ条件を満たし、重大な不整合や成功扱いされるエラーがないこと。
- 5.1の利用者数・データ量、5.2の性能・稼働率、5.3のバックアップ・復旧目標、5.4のアクセス制御を満たすこと。

## 7. 用語集

### 7.1 業務用語

**タスク：** 研修受講者が管理する作業単位。**見積り時間：** タスクに対して予定する作業時間。**実績時間：** 実際に作業した時間を日付と分数で記録したもの。**先行タスク：** 後続タスクより先に完了するタスク。**後続タスク：** 先行タスクの後に進めるタスク。

### 7.2 技術用語

**永続化：** 画面再表示後も保存済みデータを取得できること。**受け入れ条件：** 要件の充足を判定する確認可能な条件。

### 7.3 システムステータス値

**未着手：** 作業未開始。**実行中：** 作業中。**完了：** 作業完了。**並列作業可能：** 未着手で先行タスクなし、または全先行タスク完了。**並列作業不可：** 未着手で未完了の先行タスクあり。**判定不能：** 自己依存、循環依存、存在しないタスクへの参照により状態判定できない。
