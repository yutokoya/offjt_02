# ADR-002: 開発の進め方

- 状態: 採用 <!-- 提案中 / 採用 / 却下 / 置き換え -->
- 決定日: 2026-11-17
- 決定者: 研修2期参加者
- 関連資料: 要件定義書、ADR-001

## 背景・課題

スライド29に示されたテーマの性格のうち、1つめ（画面中心で作るものが曖昧）と2つめ（画面中心で作るものは概ね決まっている）の両方が関連しそうです。一方、現時点では実際の画面イメージがありません。

## 決定

- 採用する型: ①モック先行を半日試行し、その後②契約先行→③スケルトン先行→⑤機能単位の縦割りで進める
- 作業の順序:
  1. 半日: ①モック先行で画面のたたき台を作る
  2. ②契約先行で画面とサーバ間のAPI入出力を決める
  3. ③スケルトン先行で、機能が空でも端から端まで通る最小構成を作る
  4. ⑤機能単位の縦割りで機能を実装する

## 選定理由

画面中心のテーマですが、まだ実際の画面イメージがないため、①モック先行を半日だけ試して画面の方向性を確認します。また、スライド28で③スケルトン先行が全チーム必須とされているため、②契約先行の後に③を行います。以上から、①を半日試行した後、②→③→⑤の順で進めます。

## 各型の扱い

| 型 | 扱い |
|---|---|
| ① モック先行 | 半日試行する |
| ② 契約先行 | 採用。APIの入出力を決める |
| ③ スケルトン先行 | 必須のため採用。端から端まで通る最小構成を作る |
| ④ データ先行 | 今回は採用しない。画面中心のテーマのため |
| ⑤ 機能単位の縦割り | 採用。スケルトン作成後の実装に使う |

## 影響・注意点

- 利点: 画面イメージがない状態から、利用者役の確認を通じて方向性を具体化できる。
- 制約・リスク: モック作成は半日に区切り、実装に広げない。
- 利用者役に確認してもらうタイミング: ①を半日試行した後。
- 進め方を見直す条件: モック確認後も画面やAPIの方向性が定まらない場合は、チームで再検討する。
