# ADR-003: データモデル・API設計方針

- 状態: 採用（Mustの後にShould S1〜S3を実装） <!-- 提案中 / 採用 / 却下 / 置き換え -->
- 決定日: 2026-11-17
- 決定者: 研修2期参加者
- 関連資料: [ADR-001](./ADR-001-technology-selection.md)、[ADR-002](./ADR-002-development-approach.md)、受け入れ条件 M1-M3・S1-S3

## 背景・課題

フロントエンドはReact、バックエンドはSpring BootのREST API、データベースはPostgreSQLを使用する。Mustではタスクの登録・取得・更新・削除を行い、Shouldでは見積り・実績時間、並列作業状態、タスク間の依存関係を扱う。

Mustを先に実装し、その後Should S1〜S3を実装する。API契約とデータモデルは、フロントエンドとバックエンドで同じ情報・制約を扱えるように定める。

## 決定

### データモデル

1. **タスク**
   - Mustで必要なタスク名、説明、期限日を保持する。
   - タスク名は最大100文字とする。説明は任意、期限日は日付として扱う。
   - S2で必要なステータスは「未着手」「実行中」「完了」とし、初期値は「未着手」とする。
   - 担当者は任意の自由入力とし、未入力の場合は未割当として扱う。

2. **見積りと実績**
   - 見積り時間はタスクごとの値として保持する。
   - 実績時間は、タスクID・日付・分数を持つ複数の実績記録として保持する。
   - 実績合計は実績記録の合計から求め、見積りの編集では実績記録を変更しない。

3. **タスク間の依存関係**
   - 先行タスクIDと後続タスクIDを持つ、タスクとは別の関係データとして保持する。
   - 1つのタスクに複数の先行・後続タスクを登録できる。
   - 自己依存、循環依存、存在しないタスクへの参照、同一関係の重複は受け付けない。

4. **並列作業状態**
   - 「並列作業可能／不可」などの状態は保存値にせず、タスクのステータスと最新の依存関係から判定する。
   - 依存関係の情報が取得できない、または不正な関係がある場合は「判定不能」とする。

5. **タスク削除と関連データ**
   - タスクは論理削除とし、通常の一覧には表示しない。
   - 実績記録は効果検証に利用できるよう保持する。
   - 削除対象タスクを先行または後続とする依存関係はすべて削除し、他のタスクと無関係な依存関係は維持する。削除されたタスクを経由する関係は自動でつなぎ直さない。
   - 削除したタスクの依存関係は並列作業状態の判定対象から除外する。

### API契約

- JSONを使用するREST APIとする。
- MustのタスクAPIは、`/api/tasks`で一覧取得・登録、`/api/tasks/{taskId}`で個別取得・更新・削除を行う。
- Should S1〜S3のAPI設計は[API契約資料](../design/api-contract.md)に定めた内容を採用し、Mustの後に実装する。
- 入力不備はHTTP 400、対象が存在しない場合は404、重複や循環依存などの競合は409で返す。
- エラー応答は`code`、`message`、必要に応じて`fieldErrors`を含む共通JSON形式とする。
- 登録・更新に失敗した場合は部分更新を行わず、成功したように扱わない。削除成功時は204を返す。
- 詳細なリクエスト／レスポンス項目はAPI契約資料で定義する。

## 選定理由

- 実績時間を個別記録にすることで、日付ごとの確認・編集と合計の再計算ができる（S1-03〜S1-07）。
- 見積りと実績合計の差異を保存値にせず都度算出することで、見積りまたは実績の更新後も最新の差異を表示できる（S1-13）。
- 依存関係を独立した関係データにすることで、複数関係を扱い、自己依存・循環依存・重複を検証できる（S3-01〜S3-10）。
- 並列作業状態を最新情報から判定することで、タスク状態や依存関係の更新後に再判定できる（S2-07、S2-08）。
- 論理削除により通常の一覧から除外しつつ、実績記録を保持して効果検証に利用できる。
- REST APIの入出力と検証方針を先に定め、フロントエンドとバックエンドを契約に沿って開発できる（ADR-002）。
